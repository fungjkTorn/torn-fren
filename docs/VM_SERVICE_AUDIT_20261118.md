## Effective producer and consumer chain

- **Web configuration.** The running web process explicitly selects the first-ten snapshot and enables the catalog cache and light graph. The deployed bridge defines per-cohort overrides for both board and history paths. No such overrides were set in the running process at the follow-up, so challengers, next-six, and final-pair use the bridge's per-cohort defaults. The process still carries the V41 config and V75 snapshot path. Middleware returns the newer board before the legacy handler can serve the public V41-named route.
- **Versioned publishers.** Systemd working directories and drop-ins identify separate first-ten, challenger, next-six, and final-pair releases. The first-ten service executes an external reporting entry point that imports the release publisher and loads its evidence wrapper. It uses separate publisher and model revisions. The final-pair drop-in invokes an external recovery entry point against the versioned final-pair release. Japan-private invokes the final-pair module from that same release and writes to its own directory. The three added-cohort jobs read the live collector. Keep the referenced wrappers, shared Python runtime, releases, and state directories together.
- **Research configuration.** Separate exporter scripts read the collector and use a pinned roster from the V160 research stage. The research stage is therefore still an active input even though the V160 forward timer is disabled. The five-minute wrapper selects an approved model revision and uses the sanitized forward snapshot, with the older research snapshot as its explicit fallback if the forward file is unreadable. The research ledger and reports are separate from the public board. The V48 worker has an explicit active-timer prerequisite for the V38 private shadow lane.
- **Recovery and Discord.** The poller persists recovery work in the collector database. The gap worker consumes the recovery queue. The routine worker checks that queue before grading its own jobs. Discord reads the resulting local forecast evidence through V2, independently of the public beta middleware. Audit failures can degrade grading and confidence while stock and command responses remain available.

## Proposed sequence and rollback

1. **Capture a baseline.** Record each candidate's effective unit, drop-ins, release and wrapper references, timer enablement, output ages, private owners, and queue counts. Before any archival, preserve consistent SQLite copies and a manifest of paths, ownership, and permissions.
2. **Scope gap recovery separately and keep final-pair on hold.** Reproduce the recovery queue timeout on a protected copy before proposing a change. Require completed jobs and a declining routine backlog with steady stock cadence. **Rollback:** restore the recorded worker revision and unit configuration if a recovery repair regresses. Preserve current evidence and queue state. Any final-pair repair requires a separate owner decision on the exact deployed models and their public role. Keep both services and evidence in place.
3. **Review a V48 trial only after confirming the private shadow plan.** If the owner confirms V38 private shadow will stay inactive, pause only the V48 timer in a separately authorized change and let any running oneshot finish. Retain its unit and cache. Observe several publisher cycles and compare collector cadence, forecast ages per cohort, Hot List, All Items roster, prices and departures, graph history, and Discord stock and V2 commands. **Rollback:** restart the timer and restore recorded enablement if it changed. Confirm the timer fires.
4. **Keep currently collecting research jobs and fallback data in service.** Confirm who uses the older export, Japan publication, and canary. If the owner later ends an experiment and authorizes pausing it, preserve its ledger and reports first. **Rollback:** restore any paused exporter and wait for fresh input before resuming its dependent research timer. Verify issue and report freshness.
5. **Archive release copies after verifying references.** Check effective launchers, live configuration, private tools, and rollback paths. Archive only cleared copies and retain the manifest. **Rollback:** restore original paths, ownership, and permissions and verify the affected producers and consumers.

**Resource assessment.** At 8:06 p.m. EST the VM had two vCPUs, 9.2 GiB RAM available out of 11 GiB, no swap, and 29 GiB free. The existing Discord bot used about 41 MiB of service memory, the web service about 98 MiB, and the poller about 23 MiB. Load averages were 2.95 / 2.45 / 2.14, and the three one-second CPU samples after the cumulative line showed 0%–3% idle. RAM and disk have room for a small separate service. CPU headroom was limited during the sampled publisher overlap, so these measurements do not establish capacity for unrestricted work.

If separately authorized, assess an independent, outbound-only Beanstalk Gateway process with its own service identity and restart policy. Use the cached, read-only Hot List HTTP feed if it needs predictions. Estimate a **64–128 MiB working set** and start assessment with a **192 MiB memory ceiling** and **10% of one vCPU** as trial limits, subject to startup and reconnect measurements. Use bounded requests, backoff, and bounded logs. A trial should preserve collector heartbeat cadence, cohort publication age, existing Discord responsiveness, and research issue/report freshness. If it causes contention or fails to reconnect within the budget, roll back only the new service. No Beanstalk service was installed or started.

## Limits

Discord command wiring was verified from deployed source and connection status from journal summaries. The audit did not send Discord commands or exercise the All Items tab interactively. Off-VM private workflow activity, manual consumers of the Japan and research outputs, canary use, and rollback-only references require further verification. A short successful probe establishes observed availability, while longer runs are needed to measure resource savings and recovery. This report contains aggregate observations and logical artifact names only. It contains no database files, private logs, environment values, or credentials.
