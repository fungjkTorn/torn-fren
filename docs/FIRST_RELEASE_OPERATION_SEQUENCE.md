# First-release operation sequence

This change adds a read-only first-release publisher entry point. It is not
connected to any production page or service. No systemd units, collector,
existing historical results, V174 model code, or workflow definitions change.

## Required behavior

1. Build successive stock-availability forecasts from observed completed
   stocked/depleted phases. Retain the full predicted event list, including
   events that cannot be reached with the requested flight duration.
2. Include current stock if it is forecast to survive the flight. Otherwise
   inspect future events in chronological order.
3. Select the earliest reachable buying window, then calculate its earliest
   departure and latest safe departure. Calendar lookahead has no eight-hour
   limit; 64 events is an explicit compute guard. Exhaustion is reported as no
   reachable window, not as an invented prediction.
4. Run exactly the frozen configuration for that item, using departure choices
   restricted to the selected window. The timing model cannot compare later
   restocks or suppress the chosen window because of a low score.
5. If timing support is unavailable, retain the event-based departure estimate
   with an explicit `UNAVAILABLE_USING_EVENT_ESTIMATE` status. This is not a
   newly trained substitute model and does not inherit historical accuracy.
   Out-of-window timing results are rejected and explicitly reported.
6. Return departure, actual landing time, deadline, all event estimates, source
   age, threshold, model identity and refinement status. Stale data, insufficient
   phase evidence or model errors remain visible; these cannot authorize a
   confident live recommendation. Missing evidence cannot be replaced by a
   made-up restock calendar.

The event timeline is generated by the shared empirical phase forecaster.
V18/V19 are conditional timing scorers on that timeline, not ten independently
trained restock calendars. Keeping those roles explicit is part of this change.

The new first-release path uses stock **>30 (>=31)** consistently for phase
extraction, native scoring timelines and the decision contract. Legacy paths
retain their >=30 defaults. The ten-second legacy arrival offset is not used:
landing is departure + actual flight duration; success means stock at landing.
Historical rates are not silently relabelled under this changed policy.

## Execution and verification

`python -m services.first_release_schedule --source SNAPSHOT.sqlite
--item "mex:Dahlia" --flight-seconds 1020` is a read-only one-item publisher.
Run it in an isolated process against a fresh, causal stock snapshot. It never
launches a tournament, changes the source database, publishes a website or
takes a flight. The legacy engines temporarily bind their history adapter to
the read-only source; module globals are restored on success and error. Do not
invoke the native adapter concurrently inside the website process.

The operation tests exercise all ten fixed configurations with actual native
cycle extraction, features and engine planning on deterministic synthetic
SQLite data. They verify first-event priority, unsupported timing, low scores,
invalid later-event choices, current-stock reachability, different flight
durations, actual landing boundaries, stale forecasts, >30 semantics, multi-day
events and source immutability. These tests establish behavior, not accuracy.

The pre-existing event-width regression assumed the obsolete eight-hour
default. The pinned original predictor also failed that assumption. The test
now explicitly requests an eight-hour legacy horizon; separate checks assert
that first-release forecasts have no such calendar limit.

## Remaining release work

- Staging against a fresh sanitized VM snapshot, including source/country
  freshness and runtime/resource checks. The entry point currently reports
  country-specific freshness as unverified; a global heartbeat is insufficient
  to claim it has been checked.
- A single shared feed for the three views, stable event matching across
  revisions, immutable trip storage and poll-backed arrival grading.
- Last ten distinct forecast trips with success/failure/unknown/pending and
  signed timing diagnostics. `freeze_trip` supplies immutable record semantics
  but does not implement persistence or stable physical-event matching.
- Separately established live accuracy. No historical percentage is claimed
  for this changed first-event/>30 policy.
- Dependency-based replacement and retirement of old VM producers after the
  new feed is verified, with rollback.

No GitHub Actions run or production rollout is required to review this change.
